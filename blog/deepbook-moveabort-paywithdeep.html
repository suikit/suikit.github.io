DeepBook V3 MoveAbort code 3 — the silent pay_with_deep failure every bot hits

You place a limit order on DeepBook V3. The transaction aborts with MoveAbort ... 3 somewhere inside the pool module. No error string, no hint — just a numeric code that tells you nothing. If you run a bot, this is the single most common way an order silently fails.

What code 3 actually means

DeepBook V3 can charge trading fees in DEEP tokens or in the pool's quote/base coin. The choice is a flag on the order call:

tx.moveCall({
  target: `${DEEPBOOK_PACKAGE}::pool::place_limit_order`,
  arguments: [ pool, balanceManager, /* …, */ payWithDeep /* bool */, /* … */ ],
});

With pay_with_deep = true the fee is pulled from the DEEP balance held by your BalanceManager — the on-chain object your funds sit in for trading. The abort fires when that balance can't cover the fee:

  • Not enough DEEP at all. You funded the manager with SUI and USDC but never deposited DEEP — a very easy miss on a fresh setup.
  • DEEP exists but is locked. Open orders lock balances, including DEEP already committed to fees on other orders. Free DEEP ≠ total DEEP. Your manager can hold 50 DEEP and still fail a 0.5 DEEP fee.

That second case is the nasty one: the bot works for days, then starts aborting as open orders accumulate and lock more DEEP. Nothing in your code changed — the balance just crossed under the fee line.

Detect it before the abort

The fix we ship is a preflight check plus an automatic fallback:

// before building the order tx
const deep = await manager.balances(DEEP_TYPE);           // { free, locked }
const feeEstimate = estDeepFee(order);                    // from pool fee params
const payWithDeep = deep.free > feeEstimate * SAFETY;    // e.g. 3x buffer

if (!payWithDeep) {
  // pay fees in the pool coin instead — order still goes through
}

Flip pay_with_deep = false and the same order succeeds, with the fee charged against the order's own proceeds (quote/base coin of the pool). The fee is slightly different in asset terms, but the order exists — which beats a clean abort every time.

Operational rules we landed on

  • Keep a DEEP buffer. Hold ~3× the expected open-order fee load in the manager so pay_with_deep=true stays viable (DEEP fees can be cheaper depending on the pool).
  • Never hard-code the flag. Evaluate it per order against the free balance, not the total.
  • Log which path was taken. "placed @ X (deep)" vs "(pool-coin)" makes later PnL/fee accounting much easier.
  • Watch locked, not just free. If aborts start after weeks of uptime, check locked DEEP first — accumulated open orders are the usual suspect.

Result

One preflight check turned the most common silent failure into a non-event: the bot detects the shortfall, flips the fee asset, and the order still lands. If your DeepBook bot aborts with code 3, check the manager's free DEEP before you check anything else.
