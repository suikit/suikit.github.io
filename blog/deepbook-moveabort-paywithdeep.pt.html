DeepBook V3 MoveAbort código 3 — a falha silenciosa de pay_with_deep que todo bot encontra

Você envia uma ordem limite no DeepBook V3. A transação aborta com MoveAbort ... 3 em algum lugar do módulo da pool. Sem mensagem de erro, sem dica — apenas um código numérico que não diz nada. Se você opera um bot, esta é a forma mais comum de uma ordem falhar silenciosamente.

O que o código 3 realmente significa

O DeepBook V3 pode cobrar taxas em tokens DEEP ou na moeda quote/base da pool. A escolha é um flag na chamada da ordem:

tx.moveCall({
  target: `${DEEPBOOK_PACKAGE}::pool::place_limit_order`,
  arguments: [ pool, balanceManager, /* …, */ payWithDeep /* bool */, /* … */ ],
});

Com pay_with_deep = true a taxa sai do saldo de DEEP do seu BalanceManager — o objeto on-chain onde seus fundos ficam para negociação. O abort acontece quando esse saldo não cobre a taxa:

  • DEEP insuficiente. Você depositou SUI e USDC no manager mas nunca depositou DEEP — erro muito comum em setups novos.
  • DEEP existe mas está bloqueado. Ordens abertas bloqueiam saldos, incluindo DEEP já comprometido com taxas de outras ordens. DEEP livre ≠ DEEP total. O manager pode ter 50 DEEP e ainda falhar numa taxa de 0,5.

O segundo caso é o traiçoeiro: o bot funciona por dias e começa a abortar quando as ordens abertas acumulam e bloqueiam mais DEEP. Nada no seu código mudou — o saldo apenas cruzou a linha da taxa.

Detecte antes do abort

A correção que entregamos é uma verificação prévia mais um fallback automático:

// antes de montar a tx da ordem
const deep = await manager.balances(DEEP_TYPE);           // { free, locked }
const feeEstimate = estDeepFee(order);                    // parâmetros de taxa da pool
const payWithDeep = deep.free > feeEstimate * SAFETY;    // buffer de ~3x

if (!payWithDeep) {
  // paga a taxa na moeda da pool — a ordem passa do mesmo jeito
}

Com pay_with_deep = false a mesma ordem é executada, com a taxa cobrada nos próprios fundos da ordem (quote/base da pool). A taxa muda um pouco em termos de ativo, mas a ordem existe — sempre melhor que um abort limpo.

Regras operacionais que adotamos

  • Mantenha um buffer de DEEP. ~3× a carga esperada de taxas de ordens abertas no manager, para manter pay_with_deep=true viável (taxas em DEEP podem sair mais baratas conforme a pool).
  • Nunca fixe o flag no código. Avalie por ordem contra o saldo livre, não o total.
  • Registre o caminho usado. "placed @ X (deep)" vs "(pool-coin)" facilita muito a contabilidade de taxas depois.
  • Olhe o bloqueado, não só o livre. Se os aborts começam depois de semanas de uptime, cheque o DEEP locked primeiro.

Resultado

Uma verificação prévia transformou a falha silenciosa mais comum em um não-evento: o bot detecta a insuficiência, troca o ativo da taxa e a ordem entra. Se o seu bot aborta com código 3, cheque o DEEP livre do manager antes de qualquer outra coisa.
